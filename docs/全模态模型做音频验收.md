# 用全模态模型（Qwen-Omni）给音频做「感知层」验收

> 面向人读。工具用法见 `tools/audio/README.md`，脚本在 `tools/audio/omni_judge.py` 与 `audio_eval.py`。
> 本文回答四个问题：**它能做什么、不能做什么、怎么用、要花多少钱**。

---

## 0. 为什么需要它：ASR 有一个大盲区

音频验收原先只有两头，中间一大段是空的：

| 层 | 手段 | 能覆盖 | **覆盖不到** |
|---|---|---|---|
| 声学 | ffmpeg + numpy | 时长/响度/静音/削波/循环接缝 | 内容是什么 |
| 内容 | ASR（SenseVoice / Fun-ASR） | **只有语音** | 音效、音乐、环境音 |
| 感知 | ← 本文 | 音效/音乐/环境音 + 情绪/空间感 | 逐字准确度（仍靠 ASR） |

盲区有多大？实测：`暗杠.mp3`（纯牌碰音效）的 ASR 转录结果是**空字符串** ——
按 ASR 的口径它等于不存在或「废件」。而项目里有 **65 个音效 + 9 个环境音 + 5 条 BGM**
（共 79 条，占音频总量的 1/4），全在盲区里。

## 1. 它能做什么（实测，不是文档推测）

用 `qwen3.8-omni-flash` 在项目真实素材上测：

| 能力 | 实测表现 | 例子（真实输出） |
|---|---|---|
| **判类** | **93%**（15 个素材，14 对） | 音效/语音/音乐/环境音自己听出来，不看文件名 |
| **描述音效** | 很强 | 「木槌敲击声、低沉鼓声、最后一下金属镲片声」 |
| **描述音乐** | 很强 | 「木琴或马林巴琴演奏的简短明快旋律，约三到四个音符」 |
| **情绪/氛围** | ASR 完全做不到 | 「忧郁、沉思、孤寂」「阴郁、压迫、悬疑」 |
| **空间感** | 可用 | 干 / 有混响 / 空旷 |
| **语速·清晰度** | 可用 | 配音是否「略糊」「听不清」 |
| **异常检测** | **提线索**（需交叉验证） | 「多段拼接」「突然截断」「混入提示词」 |
| **顺带转录语音** | 可用，但 ASR 更专 | 台词内容比对 |

**最有价值的一点**：它能发现**语义与听感不符**。实测抓到 ——

```
文件名/提示词说：sfx-mj-clack = 两张麻将牌互相碰撞的清脆卡嗒声
它听到的：      「一声短促的提示音（类似"叮"或"咚"的单音）」
```

后来用独立的信号分析证实：那条 `flat_db=-35.3`、基频自相关 **0.96** ——
**是个纯音，不是撞击声**。提示词写「清脆卡嗒声」，模型给了个"清脆的单音"。
这类错误**声学指标抓不到**（时长/响度全部正常），**ASR 更抓不到**（返回空）。

## 2. 它不能做什么（这部分同样重要）

### ⚠ 它会对静音编造内容

喂一段 **ffmpeg 生成的、逐样本全零的 3 秒静音**，问 5 次：

```
第1次  类别=音效  内容=一段短促的电子提示音，类似游戏界面中的确认或通知蜂鸣声
第2次  类别=音效  内容=一段短促的电子合成提示音，类似游戏菜单或UI交互音效，带有轻微尾音衰减
第3次  类别=音效  内容=一段简短的游戏音效素材
第4次  类别=音效  内容=一段短促的电子提示音效，类似游戏界面交互或通知音
第5次  类别=静音  内容=音频中几乎没有可辨识的声音，接近完全静音
```

**4/5 次是编的。** 但注意第 5 次它答对了 —— 说明**它不是"听不见"，是"被提问方式带着走"**：

| 提示词写法 | 静音识别 |
|---|---|
| 「这是一段游戏音频素材。请判断类别：语音/音效/音乐/环境音/静音」 | 1/5 对 |
| 「请判断这段音频里**实际**有什么…若几乎听不到任何声音，**必须**选「静音」，**不要猜测或补充并不存在的内容**」 | 4/4 对 |

**结论：幻觉率由提示词决定。别让提示词预设「里面一定有内容」。**

### ⚠ 不能做细粒度音质判断

- 它说「突然截断」时，对多数素材都是**误报**（实测 5 条里 4 条误报）
- 「循环接缝是否超过 6dB」它答不了 —— 那是 `check_bgm.py` 用 RMS 差算的
- 「响度是否达标」也不行 —— 那是 `check_audio.py` 用 LUFS 算的

**凡是能用数字精确表达的，都不要问模型。**

### ⚠ 不能判旋律相似度 / 版权

它会描述"听起来像什么风格"，但**不能**用来判断"是否与某曲相似"。
版权问题只能靠人工与法务。

### ⚠ 输出不可复现

同一段音频两次调用可能给出不同措辞。所以：

- **不要拿它的输出做通过/失败的唯一依据**
- 需要稳定判断的，让它输出**结构化 JSON** 的枚举字段（类别/语速/清晰度），而非自由描述
- 关键结论至少跑两次，看是否一致

## 3. 怎么用

### 3.1 凭据

```powershell
$env:DASHSCOPE_API_KEY  = "sk-..."         # 百炼控制台 → API-KEY 管理
$env:DASHSCOPE_BASE_URL = "https://{业务空间}.cn-beijing.maas.aliyuncs.com/compatible-mode/v1"
```

> 文档示例用的是**业务空间专属域名**；百炼也有通用兼容域名
> `https://dashscope.aliyuncs.com/compatible-mode/v1`。
> **地域必须和 API Key 一致** —— 北京 key 打新加坡域名会失败。

### 3.2 本地文件怎么传：base64 内联

文档示例都用**公网 URL**，但本项目的素材在本地，且分发包含**授权未核实的第三方素材**
（不该传到任何公开位置）。所以走 base64 内联：

```python
{"type": "input_audio",
 "input_audio": {"data": f"data:audio/mpeg;base64,{b64}", "format": "mp3"}}
```

**限制**：编码后的 Base64 字符串必须 **< 10MB**。
所以**先转 mp3 再传** —— wav 是未压缩的，本项目最长的 BGM 是 106 秒，
转 wav 是 10MB、base64 后 13MB，**直接超限**；mp3 同样内容 1.7MB，完全够用。

### 3.3 两个工具

```powershell
# ① 可信度自检（必跑！用「已知答案」的对照件验证模型是否在编）
python tools\audio\omni_judge.py --selftest

# ② 批量判类（真实素材，看它能不能自己分清音效/语音/音乐）
python tools\audio\omni_judge.py --batch --per-cat 3

# ③ 单文件深挖
python tools\audio\omni_judge.py --file x.mp3 --ask "这段音频的结尾是否自然收束？"

# ④ 综合评估器（声学 + 音色 + 内容 + 感知 四层合一，推荐日常用这个）
python tools\audio\audio_eval.py <目录或文件>
python tools\audio\audio_eval.py <目录> --no-omni      # 离线免费，只跑前三层
```

### 3.4 分层裁决规则（`audio_eval.py` 的设计）

```
声学/音色/内容层  → 能否决（FAIL），因为它们是精确量
感知层（Omni）    → 只能提示（SUSPECT），因为它会幻觉
两层冲突时        → 以精确层为准，并标注「模型可能幻觉」
```

例：模型说某条是「静音」，但声学显示峰值 −2dB → **以声学为准**，记一笔模型误报。

## 4. 选哪个模型

| 模型 | 输出 | 上下文 | 评价 |
|---|---|---|---|
| **`qwen3.8-omni-flash`** | 文本 | 1M | **推荐**。音视频理解主力，支持深度思考/工具调用/联网搜索 |
| `qwen3.5-omni-plus` / `flash` | 文本 + **语音** | — | 需要模型"出声"时用。**本项目音色由 StepAudio 定，用不到**（且贵） |
| `qwen3-omni-flash` | 文本 | — | 输入仅支持文本 + **单一**模态，且音视频限 **150 秒**，不如上面 |
| `qwen-omni-turbo` | 文本 | — | **已停止更新** |

**本项目选 `qwen3.8-omni-flash`**：只要文本输出、要长音频（BGM 106 秒）、要便宜。

### 关于「不需要它输出音频」

正确。本项目**生成**音频走 StepAudio（音色可控、限免），
**理解**音频走 Omni（只要文本）。
两者的分工不要混：让 Omni 出声等于放弃音色一致性控制，而且贵得多。

## 5. 成本

计费按 token，不同模态（音频/图像/视频）折算成 token 数。实测量级：

| 场景 | 输入 token | 输出 token | 说明 |
|---|---|---|---|
| 单条短音效（0.3~0.8s） | ~140~190 | ~180~270 | 一条一次调用 |
| 单条 BGM（106s） | 会大很多 | ~250 | 长音频按秒折算 |

**节省办法**（都已实现在工具里）：

1. **只抽样**：不必全量。65 个音效用 `--per-cat 4` 抽 4 条就能看出系统性趋势
2. **先离线跑前三层**：`--no-omni` 免费，只有声学/内容层过不了的才需要问模型
3. **一次问全**：提示词里一次要回类别+情绪+空间感+语速+清晰度+异常（结构化 JSON），
   而不是分 6 次问
4. **`reasoning_effort="low"`**：评估任务不需要深度思考，默认 xhigh 会浪费输出 token

> 定价以百炼控制台为准。**别在文档里写死单价** —— 会变，而且各地域/各模型不同。

## 6. 与其他两条外部模型力量的关系

项目现在有三条互相独立的外部模型链路，各自负责一种模态的**生成**或**理解**：

| 链路 | 服务商 | 干什么 | 凭据 | 文档 |
|---|---|---|---|---|
| **`stepaudio-gen`** | StepFun 阶跃星辰 | **生成** 音频（配音/音效/环境音/BGM） | `STEP_API_KEY` | 本目录 `stepaudio-音频素材制作.md` |
| **`lovart-image`** | Lovart | **生成** 图片（立绘/贴图/背景/海报） | `LOVART_AK` / `LOVART_SK` | skills 里的 `lovart-image` |
| **`omni-audio-eval`** | 阿里云百炼 | **理解** 音频（音效/音乐/环境音的感知层验收） | `DASHSCOPE_API_KEY` | 本文 |

三者**不可互相替代**：

- StepAudio 生成完，**没有**理解能力 —— 它不知道自己生成的对不对
- Omni 能理解，但**不能**生成音频（也不需要，音色由 StepAudio 控）
- Lovart 只管图片，与音频链路无交集

验收闭环因此是：**StepAudio 生成 → 声学层 + 音色层 + ASR 层 + Omni 感知层 四层验收 → 入库**。

---

## 7. 一句话总结

> **Omni 管「这是什么、什么感觉」，声学层管「是否合格」，ASR 管「念得对不对」。**
> 三者互补。而且 Omni 的输出必须被另外两层交叉验证 ——
> 它对一段纯静音能编出「游戏界面提示音」。
