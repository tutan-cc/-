## 3. 因规则变更而同步的既有用例（原期望 → 新期望 → 原因）

1. 「一食物只能进对应**厨具**」→「9 **列**一一对应（食材↔灶位↔盘）」：绑定粒度从厨具种类细化为一一对应的列；`stationIndexOfKind` 取值随之改变（pot 0-2 / griddle 3-5 / steamer 6 / counter 7 / juicer 8）。
2. 食材桶 8 样 → **9 样**，`FOOD_IDS` 顺序改为**列序**（白粥/热牛奶/清汤/煎蛋/培根/三明治/包子/沙拉/果汁）：底部食材桶 = 列，桶序即列序。
3. 「备菜盘限量 ×3」→「9 列各 1 专属盘」：用户明确要求「每个锅都配备一个空盘」。`PREP_PLATES` 保留为兼容名（=9），`serveStationIndices()` 由 `[3..8]` 变为 `[]`。
4. 出餐窗口 `SERVE_WINDOW` 3.5s（锅内）→ **4.5s（盘上「过火计时」）**：用户建议的 4.5s，且压力点从「锅里」移到「盘上」。
5. 热乎度阈值 4s / 11s → **1.5s / 3.0s / 4.5s**（三段均分在过火窗口内）：盘上总寿命被收紧到 4.5s 后必须重分档，否则永远停在「热乎」；**三档分数 14 / 10 / 6 逐字不变**。
6. rules 层 `autoPlate` 默认 false → **true**：「熟了自动落到本列专属盘」由可选机制升级为核心规则；仍可用 `autoPlate:false` 关掉（按住看火 / 调试手感）。
7. 「现做灶位完成不落盘、锅内出餐窗口」→ **全部落盘**：不再分两类灶位。`takeReady / openServeWindow / expireServeWindows` 作为**兼容纯函数**保留但已不进入主循环（单测仍覆盖它们的旧语义）。
8. 原因码 `wrong-kind`「这个灶位放不了它」→ `wrong-column`「那是别人的锅 —— 每样食材只进自己那一列」：列绑定取代厨具种类校验。
9. 「盘上停 12s 照样能上（凉 6 分）」→「**4.5s 内必须送，超时糊掉只能丢**」：用户要求的过火报废压力。
10. 顾客卡 372×302 → 372×**210**：给 9 列列对齐让出竖直空间；断言 `cards.h ≥ 300` 改为只校验宽度（≥220）。
11. 旧文案断言（`备菜盘 ×3` / `现做现送` / `无备菜盘` / 8 样食材）→ 新文案（`9 列 × 每列 1 锅 1 专属盘` / `点我下锅` / 三条操作图例 / 9 样食材），并**新增反向断言**：旧文案必须不再出现。
12. `st.tossed` 语义：只在丢糊掉的份时 +1 → **每次丢弃都 +1**：双击丢弃是新操作，结算面板需要「丢过几次」的完整账。
13. `finish()` 结果字段：`prepPlates: 3` → `prepPlates: 9`（兼容）并新增 `platesTotal / columns / plateLife`；结算面板「出餐预备」文案改为「N 份（9 列专属盘）」，「忘出锅」改为「忘取」。

## 6. 我对新操作模型的平衡判断

**过火窗口设 4.5s 是否合适？——倾向「可以，但「热乎」档偏紧，建议留一个调参口」**
- 4.5s 作为**总寿命**是合理的：一局 75s 要服务 8 位（约 16 份），9 列并行、每列「下料 → 3~5s 熟 → 落盘」的循环 ≈ 4~6s，**4.5s 的取餐窗口正好和「一列做完」同量级**，不会出现「刚转身就报废」的挫败，也逼出「忘取就报废」的手速压力。
- 问题在**三段均分**：热乎只剩 **1.5s**，而人类从「盘上闪绿」到「点下去」的反应 + 移鼠标通常在 0.6~1.2s；9 列同时催的时候，多数份会掉进「温 10 分」。实测机器人（每帧点击）能拿 100% 热乎（14.5s 通关、270 分），但人做不到。
- 建议（不改变我已实现的规则，只给调参方向）：把 `HEAT.hotSec` 从 `SERVE_WINDOW/3` 放宽到 `2.0s`（温 2.0→3.4，凉 3.4→4.5），或者总窗口 4.5 → **5.5~6s**。`SERVE_WINDOW` 与三段阈值都在常量区，改一个数即可，单测/证据链里的边界断言都按常量写，不会失效。
- 另外「糊了只能双击丢」+ 盘上 14s 自动清（沿用旧机制）是合理的兜底：不会因为一列忘取而永久堵死。

**单击送客的自动选人逻辑在高峰会不会误送？——不会「送错菜」，但确实存在「三选一」的取舍风险**
- 安全性：候选只在「订单里有这份 **且** 还没拿到这份」的顾客里挑，所以**绝不会出现 −5 的上错菜**；给过的不再重复给；没人要就坚决不消耗。
- 风险 1（抢单）：两位顾客都要煎蛋，盘只有一份 → 一定给**耐心最少**的那位。这是用户明确要的规则，方向正确（先救快走的）；副作用是耐心充裕的那位可能被动等更久 —— 但这本来就是要玩家自己「再点一份食材」解决的，符合手速玩法。
- 风险 2（无效投喂）：最急的那位如果还差 3 样、耐心只剩 0.4s，这一份很可能「喂进去也留不住人」。若要进一步优化，可在「耐心最少」之上再加一条**便宜的二次判据**：同耐心档内优先「只差最后 1 样」的顾客（关门送客、腾座位最快）。这会改变用户口述的优先级，所以**我没有擅自加**，只把它记为后续可选项。
- 风险 3（连点）：双击判定窗口 350ms 意味着「能出餐的盘」第一下就送出去了，第二下落在空盘上只会提示「盘里还空着」—— 也就是**双击丢弃只在「单击本来就送不出去」（糊了 / 没人要）时才生效**。这是为了让手速优先、不给每次出餐加 350ms 延迟；如果希望「任何时候双击都能倒掉好菜」，需要把单击改成延迟 350ms 执行，代价是出餐手感变钝，我不建议。
