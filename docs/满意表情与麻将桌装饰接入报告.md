### 2.5 ⚠ 本轮发现的真实缺口（未改玩法，如实报告）

`serveFoodToCustomer`（`breakfast.js` L774）在**订单全部拿到的同一帧**就执行 `c.left = true`（"立刻让出座位"），
而 `render()`（L2448）只画 `activeCustomers(st)`，该函数（L521）过滤掉所有 `left` 的顾客
→ **在真实玩法里，「满意」那张脸一帧都画不出来**（顾客卡片当场消失，只有飘字）。

- `debug.serveAll()` 是特意「只标 done、不置 left」的调试口子，所以出图 / 断言能看到 happy 脸。
- 本轮我**没有改这条链路**：它牵扯卡位编号、点击热区映射（`hitCustomer` 用 `activeCustomers` 下标）、顾客进店节奏与列对齐基线图，超出「补头像 + 接入贴图」的授权范围。
- 因此 `_e2e_bf_headless.cjs` 的新断言用「1ms 帧（< 1/60s 步长阈值 → 不推进 step，只渲染）」稳定命中那一帧 —— 这证明的是**贴图映射与回退链在真渲染器里是通的**，不代表真实玩法能看到。
- **若要让人眼在真实玩法里看到满意脸**，最小改动方案（未实施）：在 `render()` 里对「`left` 但未满 1.3s」的顾客补画一张卡到 `customerCardBox(list.length)`（仅当 `list.length < LAY.cards.n`），不参与点击 / 占座 / 计分。约 +5 行，但会改变 `bf_game_bg2.png` 这类视觉基线图，建议单独一轮做。

所以**故意不接**，并把这条决策写进 `debug.art().fallback` 声明里（可被断言读到）。

但倒计时文字 / 进度条是**渲染帧**（rAF；IE11 没有 rAF 时靠 200ms 兜底帧）填的 → 会偶发读到空值
（本轮实测撞到过 1 次：`通过 140，失败 3 | win_countdown: | win_barw: / left=2984ms`）。
改成**轮询等它出现**（最多约 1.2s，断言本身仍然是「必须出现且数值合法」，没有放松），
并把轮询耗掉的时间从后面那次等待里扣掉 → 「3 秒后自动过」那一段的时序一点没变。
改完连跑 4 次：`142/142` 稳定全绿。
