## 0. 两条主线：Gen 与 TTS

StepAudio 有**两个端点**，用途完全不同，别混：

| | Gen（生成） | TTS（语音合成） |
|---|---|---|
| 端点 | `POST /v1/audio/generate` | `POST /v1/audio/speech` |
| 模型 | `stepaudio-3-gen-preview`（限时免费） | `stepaudio-3-tts`（约 2.5 元/万字符） |
| 输入 | 自然语言描述（`roles` + `scripts` + `instruction`） | 固定 `voice` + 要念的 `reading` 文本 |
| 临时文件级强一致 | **每次都是新采样，音色会漂移** | **同一 voice 全程一个音色** |
| 适合 | 音效、环境音、BGM | 配音、牌名播报 |

**选型判据（这是踩过坑才明白的）**：
同一个角色要念很多句时**必须用 TTS**。Gen 是「按角色描述演一遍」，
每句都是一次新采样 —— 同一个角色报 43 张牌可能听起来像好几个人。
TTS 指定固定 `voice` 才有一致的音色。

`step_gen_audio.py` 用**有没有 `voice` 字段**来区分两种任务：
有 `voice` 走 TTS，否则走 Gen。

## 1. Gen 的请求结构与三个要点

```json
{
  "model": "stepaudio-3-gen-preview",
  "task": "text_to_audio",
  "roles": [
    { "name": "打牌的人", "description": "成年男性，嗓音厚实略带沙哑，报牌干脆利落" }
  ],
  "scripts": [
    { "text": "[麻将牌碰撞的清脆声]" },
    { "speaker": "打牌的人", "text": "（利落报牌）五万" }
  ],
  "instruction": "室内麻将桌旁，安静环境，不要背景音乐和回声",
  "response_format": "mp3",
  "sample_rate": 48000
}
```

| 元素 | 写法 | 决定什么 |
|---|---|---|
| `roles[].description` | 自然语言描述音色/年龄/情绪/口音 | **谁在说** |
| `scripts[].text` 的 `()` | `（利落报牌，语速偏快）五万` | **怎么说** |
| `scripts[].text` 的 `[]` | `[麻将牌碰撞的清脆声]` | **音效 / 环境音 / 音乐**，可不带 speaker |
| `instruction` | 全局环境与基调 | **在什么场景** |

**上限（超了直接 HTTP 400）**：`roles` 合计 500 字符 · `scripts` 合计 1000 字符 · `instruction` 500 字符。

**不支持**：`voice`、`voice_label`、`timestamp`。

**没有 `duration` 参数** —— 时长不可控。实测同一批 BGM 出来 17.6~106.6s。
用提示词表达意图（「只演奏一段约 30 秒的完整段落」），接受结果。

### 提示词踩过的坑

| 写法 | 结果 | 结论 |
|---|---|---|
| `pronunciation_map: {"筒":["tong3"]}` | 「一筒」被念成「一痛酸」 | **别用**，比不加更差 |
| `text_normalization: "enhanced"` | 「1978」仍读错 | 改用汉字写法「一九七八」绕开 |
| `instruction` 全局控情绪 | 「自摸」被读糊成「子摸」 | 情绪写进文本的 `（）` 更稳 |
| `（兴奋而克制）自摸` | **HTTP 451 内容审核拦截** | 「克制」+「自摸」组合误判；换简单情绪词 |
| 「结尾自然收回到开头、可无缝循环」 | BGM `dark` 末尾 2.5s 渐弱到 −41dB | 被理解成音乐性淡出 → 循环断点 21.1dB。**要明确写「不要渐弱，不要淡出收尾」** |
| 「时长约 30 秒」 | `calm` 出了 184s，能量包络强周期 0.53 | 被理解成「把 30 秒重复铺满」→ **要写「只演奏一段，不要重复铺满」** |

> **通用教训**：自然语言的否定/约束比肯定描述更容易被忽略。
> 想约束什么，就用明确的祈使句写出来（「不要…」「只…」），别指望模型从
> 「可无缝循环」这种正面目标反推出「所以不能淡出」。

## 2. 后处理：判据与三个走过弯路的地方

用 `tools/audio/process_sfx.py`，**必须用 `--preset`**，别手写参数 ——
同一组 `rel_db` 对 60 秒环境音和 0.3 秒单字的意义完全不同。

### ① 内容边界检测：不能用绝对阈值，也不能用「底噪 + 偏移」

实测数据（这就是为什么）：

```
2条.mp3   底噪 -77dB，但前 0.6s 有一段 -47dB 的房间/呼吸声，真正内容从 0.76s 开始
```

| 判据 | 结果 |
|---|---|
| 绝对阈值 −50dBFS | 房间声 −47dB 高于阈值 → **整段误判成有声**，裁剪失效 |
| 底噪 + 14dB（= −63dB） | 房间声比它还高 16dB → **同样误判** |
| **参考电平 − rel_db** ✅ | 内容与房间声差 20dB 以上 → **干净分开** |

参考电平用**响亮帧的 90 分位**，不是样本峰值 ——
音效里常有极短瞬态尖峰（转动卡位、牌碰的一下），
用峰值算阈值会把阈值抬得过高，导致**持续较长但电平略低的主体内容被判成静音**
（实测 `sfx-cir-rotate` 真实内容约 1.5s，用峰值判据只认出 0.02s）。

### ② 淡入不能设长

把淡入设成 20ms 时，整批素材的起手 20ms 全被淡掉（起点能量比峰值低 40~66dB），
游戏里点牌就「慢半拍」。淡入只为防爆音，**5ms 足够**。

> 自查方法：对比原始件与加工件的起手落差。实测原始件中位 **99.0dB**、加工件 **48.6dB** ——
> 加工后大幅改善，说明剩下的落差是语音自身软起音，不是处理造成的。

### ③ 不要用「占原始时长比例」做裁剪保护

实测不少条目真正有声的部分只占全长 **6%**（例如「过」4.82s 里只有约 0.3s 是人声，
其余全是房间底噪）。按比例设保护阈值会把这种**正当的裁剪**全部误拦。
正确做法是用**绝对下限**（0.12s）。

### ④ ⚠ 「保留最长段」会**静默丢句** —— 台词必须用 `keep_all`

这条是后期才发现的，后果最严重。

原设计是「保留最长连续有声段」。多句台词在句间停顿超过 `gap_tol` 时，
**其余的句子会被整段丢掉，而且不报任何错**：

```
investor_s0.mp3（顾曼）
  0.2~2.1s  「连踩七个风口的年轻人」   ← 被丢掉的
  2.2~2.9s  停顿 −76dB（0.8s）              ← 恰好越过 gap_tol=0.8
  3.0~3.2s  「坐」
  4.0~5.6s  「证明给我看，不是运气。」
加工件 5.10s → 2.79s，首句消失
```

复查全部 54 条台词，`rent_s1.mp3` **真的少了后半句**「可你总得给我个准话。」（1.72s → 4.03s）
—— 这是玩家能听出来的。

`--preset voice` 现在内含 `keep_all=True`：取「**首尾有声帧**」而不是长度择优。
代价是可能多留一点段间房间声，但**「多留一点静音」远好于「少说一句话」**。

> **通用教训**：「择优」逻辑用在「内容必须完整交付」的素材上就是错的。
> 而且丢句不留痕迹，必须**主动验证内容完整性**（ASR 覆盖率）才可能发现。

### ⑤ BGM 的循环接缝

BGM 是 `a.loop = true` 循环播放的，接缝处电平跳变就是每次循环「咔」一下。
`--preset bgm` 会做**等功率交叉淡化**（尾→头叠 1s）。
判据：末尾 150ms RMS 与开头 150ms RMS 的差，**>6dB 就会听出来**。
用 `check_bgm.py` 量。

> 但工具只能盖 1s。若生成出的收尾本身是 2.5s 渐弱，仍剩 14dB ——
> **必须从提示词层面禁止淡出**，工具兜不住。

## 3. 验证口径

### 3.1 本地 ASR（推荐，离线免费）

**用本机 SenseVoice 把音频转录回文字，跟预期一比就知道内容对不对** ——
这是唯一能验证「说的是不是这个词」的手段。声学指标（时长/响度）抓不出内容错误。

```powershell
python tools\audio\asr_local.py "目录"                 # 单纯转录
python tools\audio\verify_audio_content.py "目录"       # 台词：转录 + 与预期比对
python tools\audio\verify_mj_asr.py                     # 牌名：拼音同音 + 跨座位共识
```

依赖：`pip install sherpa-onnx pypinyin`（纯推理引擎，不依赖 torch）。
模型自带 `test_wavs/`，可先跑一遍确认环境正常
（`zh.wav` 应转录出「开饭时间早上9点至下午5点。」）。

**判定分四类**：`OK`（含同音字）· `PARTIAL`（多字/漏字）· `MISMATCH`（对不上）· `NOSPEECH`（无声）。

> ⚠ **这套判定有明确的能力边界，别把 OK 当「音频完美」**：
> ASR 遇到同音字会随便挑一个写出来（筒→桶/同/桐/铜/童/统/通/痛 全算通过）。
> 所以它能证明**「读音大致对」**，**不能证明读音准确**。真要确认发音标准，只能人耳听。

#### ASR 的两个必须知道的局限

**(a) 对短促喊牌识别率低 —— 单条判错不可信。**
「杠」被听成「告/干/大」、「碰」被听成「哼」是常态，`0.2~0.4s` 的语音在 ASR 里本就难。
实测 27 条「疑似错」里**没有一条是真坏件**（第一版用手写近音字表误报 40+ 条，更糟）。
唯一可信的判据是**跨座位共识**：同一个词 4 个座位全判错才可能是真坏件。
`verify_mj_asr.py` 因此把「疑似错」当诊断信息输出，**只有空白/废件才让它退出 1**。

**(b) 会把口语数字写成阿拉伯数字。**
「连踩七个风口的年轻人」转录成「连踩7个…」。比对前**必须做汉字数字归一**，
否则完全正确的音频会被误报成错。

### 3.2 云 ASR（不推荐）

StepFun 的 ASR 很便宜 —— `stepaudio-2.5-asr` 仅 **0.15 元/小时**。**但实测两个坑**：

1. **它要公网可访问的音频 URL，不接受直接上传文件**
2. 把音频传到临时 CDN 后，仍可能报 `stage=audio_download: failed to download audio`
   —— 临时带鉴权的链接它拉不到

所以云端只适合音频已在公开 URL 上的场景。**本机素材一律走本地 ASR。**

### 3.3 声学指标（脚本自动，与 ASR 互补）

| 检查 | 手段 | 能发现什么 |
|---|---|---|
| 是不是有效音频 | 文件头（`ID3` / `FF FB`）+ ffprobe | 空文件、损坏 |
| 时长对不对 | ffprobe | 生成失败但落盘了 |
| 有没有声 | 峰值 / RMS dBFS | 全静音、音量过低 |
| 起手干不干净 | 前 20ms 能量 vs 峰值 | 前导静音没裁掉、淡入过长 |
| 尾部有没有硬切 | 末 100ms 分 5 段的能量走向 | 自然衰减被切掉（会有「啪」声） |
| 整体一致性 | 各条响度/时长分布 | 忽大忽小 |
| 内容互不重复 | 声学指纹两两比对 | API 返回了同一段音频 |
| **BGM 循环接缝** | 末尾 150ms vs 开头 150ms RMS | 循环断点（`check_bgm.py`） |

### 3.4 ⚠ 接线核对：唯一能抓到「断言全绿但没声音」的一层

`AudioSys` 全层是「有文件用文件，缺失回落合成」。设计本身是对的，
但它让**「素材缺失」与「素材接错」在断言层面完全无法区分**。
实测 1542 项断言全绿的情况下，牌桌上「暗杠」「补杠」完全没有声音：

```
VOICE_NAMES 登记了它们 → 素材侧按设计不生成（手上动作用牌碰声）
→ 四个座位全 404 → Audio 无 error 兜底 → say() 只看对象非空 → 静默丢弃
```

所以必须**主动探测存在性**：

```powershell
cd 仓库根 && python -m http.server 8000    # 另开一个窗口
node tools\e2e\audio-wiring.js              # 把每个 URL 发 HEAD 看状态码
```

它覆盖：四座位牌名集合一致性 · 每个素材文件 HTTP 200 · 牌名 URL 可解析 · 抽样可实际播放。
**改完任何素材都要跑它。**

## 4. 给项目加新音频的完整流程

```powershell
# ① 写任务表（或用现成的 gen_sfx.py / gen_bgm.py / gen_mj_by_seat_tts.py）
#    提示词照第 1 节的三个要点写；台词类必须带 voice 字段（走 TTS）

# ② 生成到**工作区**（绝不直接写素材库 —— 加工前的东西不该进分发源）
python tools\audio\step_gen_audio.py --jobs new.json --out "$env:DSH_WORK_ROOT\xxx_raw" --sleep 1.5

# ③ 体检原始件（先看有没有生成失败/全静音，别急着加工）
python tools\audio\check_audio.py "$env:DSH_WORK_ROOT\xxx_raw" --min-peak -30

# ④ 后处理到素材库（用 --preset，别手写参数）
python tools\audio\process_sfx.py --src "$env:DSH_WORK_ROOT\xxx_raw" --out "...\audio\xxx" --preset sfx

# ⑤ 体检加工件（严格口径）+ 内容核对
python tools\audio\check_audio.py "...\audio\xxx" --min-dur 0.15 --max-dur 3.0 --min-peak -24
python tools\audio\verify_audio_content.py "...\audio\xxx"

# ⑥ 更新清单（纳入版本管理）+ 逐文件校验 SHA256
powershell -File .\pack-media.ps1
powershell -File .\link-media.ps1

# ⑦ 接线核对 + 跑项目测试
node tools\e2e\audio-wiring.js
powershell -File .\run-all-tests.ps1
```

**为什么 ② 要生成到工作区**：素材库是要分发给协作者的，只该放成品。
原始件混进去会白白撑大分发包、污染清单（实测曾把三份座位原始备份打进包，多 3.5MB）。
`pack-media.ps1` 现在也会排除下划线开头的目录作为兜底。

## 5. ⚠ 生成不确定：**重跑不等于更好**

StepAudio 是采样式的。**音效/人声的随机性还能接受，音乐的不确定性非常大。**
实测用**同一份提示词**把 5 条 BGM 全部重跑，结果明显更差：

| mood | 第一次（保留） | 同提示词重跑 |
|---|---|---|
| calm | 106.6s · 接缝 1.8dB | 77.9s · 3.7dB |
| city | 31.8s · 4.4dB | 47.2s · 0.8dB |
| tense | 28.8s · 2.3dB | 45.3s · 2.5dB |
| night | 17.6s · **0.7dB** | 73.0s · **12.4dB** |
| dark | 86.2s · **2.1dB** | 218.3s · **6.5dB** + 强周期 0.69 |

所以：

- **重跑前先备份当前达标件**（成品是最好的参照，不是原始件）
- **跑完必须重新验收**，别看脚本没报错就当成功了
- `gen_bgm.py` 已内置自动验收，不达标会报错并提示「先备份当前达标件」

> 同理，座位牌名也遇到过：`speed=1.2` 那次合成出 3.24s 的废件（正常 0.6s）。
> **别用参数的平台边缘值**，取中间偏稳的位置。

## 6. 批量生成的时间与限速

- **`--sleep` 是必须的**：Gen 端点实测有过限速；`--sleep 1.5` 在充值后的额度下
  实测 40 req/min 无 429。**早期撞 429 的真正原因是 sleep 设得太小，不是额度不够** ——
  别一遇到 429 就去充钱，先看 sleep。
- 单条请求约 **1.5 秒**（含往返）。43 条座位牌名 ≈ 70 秒。
- 台词 54 条约 2000 字符，走 TTS 的字符计费；素材总量小，成本可以忽略。
